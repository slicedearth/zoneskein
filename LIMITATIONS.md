# Limitations

## DNS observations

ZoneSkein queries recursive resolvers, not authoritative nameservers directly. Results are point-in-time resolver observations affected by caches, resolver policy, DNS filtering, EDNS behaviour, and network conditions. Comparing three resolvers does not establish global propagation.

Skein Map asks a fixed ten-type question set and shows named dependencies without recursively expanding them. Its graph is a presentation of the retained evidence bundle, not an inferred ownership, control, trust, or reachability graph. Resolver comparison can identify answer-data, response-code, TTL, authenticated-data, Extended DNS Error, incomplete, and unavailable differences. It cannot determine from those observations alone which result is correct or whether a difference was caused by cache age, split horizon, filtering, policy, network failure, authoritative inconsistency, or an attack.

DNS-over-HTTPS queries carry all-zero RFC 8467 padding to the next 128-octet message boundary. This reduces exact wire-length variation but does not hide the DNS question from the selected resolver, conceal timing or request counts, generate cover traffic, or ensure that responses are padded. GET transports expose a base64url-encoded padded message length to the browser and resolver even though the HTTPS connection protects it from ordinary on-path inspection.

When supplied, Extended DNS Errors are resolver-provided explanations rather than independently verified conclusions. Negative-cache guidance uses the lesser of the authority SOA TTL and SOA MINIMUM field; a response without the required SOA is not cached as a negative answer by ZoneSkein. Resolution failures never inherit authority TTLs: repeated failures use a bounded in-memory backoff from five seconds to five minutes and a later successful response clears that failure history.

The browser must permit cross-origin DNS-over-HTTPS requests. Enterprise policy, extensions, regional resolver behaviour, or temporary CORS changes may block a resolver independently of DNS itself. Quad9 requires an end-to-end HTTP/2 or HTTP/3 path for direct DNS-over-HTTPS; a browser, VPN, inspection product, or network proxy that forces HTTP/1.1 can make its direct path unavailable without establishing anything about the queried DNS name. The single Quad9 option tries the first question directly, then locks that run to direct mode after a valid response. A qualifying transport, timeout, or HTTP failure instead locks the run to **Quad9 (compatibility mode)** and retries that question through the same-origin Netlify relay only to Quad9 over HTTP/2. It does not fall back after cancellation, browser or relay rate limiting, a DNS response, a malformed response, or a local work-bound failure. Compatibility mode changes the privacy boundary because Netlify receives the question as well as ordinary connection metadata; the interface and exports identify that path.

## DNSSEC

ZoneSkein starts with a bundled, reviewed IANA root trust-anchor set, verifies each root, DS, and DNSKEY RRset locally, compares DS digests, and uses authenticated NSEC or bounded NSEC3 evidence to distinguish exact insecure delegations from missing evidence. It can then validate selected exact-positive A, AAAA, CAA, CNAME, HTTPS, MX, NS, PTR, SOA, SRV, SVCB, TLSA, TXT, and ZONEMD RRsets with the authenticated containing-zone keys. Resolver AD flags remain evidence only and never decide the local result.

The validator is intentionally narrower than a general-purpose recursive validator. For its selected application types it can authenticate exact positive and NODATA answers, NXDOMAIN, wildcard synthesis or wildcard NODATA, and bounded CNAME, DNAME, and SVCB/HTTPS AliasMode continuation. A direct CNAME inspection authenticates that CNAME RRset as the requested result; when another type is requested, every followed alias and the final RRset must authenticate. Divergent authenticated AliasMode targets remain Incomplete because selecting one would discard a signed branch and following all branches would exceed the validator’s single bounded continuation contract; ZoneSkein does not choose or query one arbitrarily. RSA, ECDSA, and Ed25519 signature operations use browser Web Crypto. RSA validation rejects moduli shorter than 1,024 bits or longer than 4,096 bits. Ed448 uses one locked, independently reviewed cryptographic primitive because Web Crypto does not expose Ed448; ZoneSkein retains the DNS wire binding, canonicalisation, key policy, work limits, and result classification. The validator bounds questions, alias transitions, response bytes, records, keys, signatures, digests, cryptographic attempts, NSEC3 work, and wall-clock network waits. RSA/SHA-1 algorithms 5 and 7 remain available for legacy RRSIG validation, but RFC 9905 DS records using them are treated as insecure rather than secure delegation paths. A final authenticated conclusion requires every supporting signature and trust anchor to be current at one common instant, and a secure evidence bundle records its earliest supporting signature expiry.

NSEC3 Opt-Out proves that a covered name may or may not exist as an insecure delegation. ZoneSkein therefore stops with an explicit Opt-Out result instead of labelling it an authenticated insecure delegation, and does not use Opt-Out to authenticate application NODATA, wildcard synthesis, or name existence. DNAME boundary, Unsupported, Incomplete, Insecure delegation, Not a delegation, Bogus, and Locally validated outcomes also remain distinct.

Bundled anchors are checked by a maintenance command against IANA’s detached CMS signature and a reviewed, pinned ICANN root certificate. Each result reports whether that release-time review is current, due after 45 days, or overdue after 90 days, and separately warns when the pinned certificate is within 180 days of expiry. This is not RFC 5011 automated rollover. A stale build can therefore become unable to establish current trust and must be updated.

The local lifecycle model compares at most 256 supplied DNSKEY or CDNSKEY records and 1,024 supplied DS or CDS records, recognises the standard CDS and CDNSKEY deletion signals, and derives supported SHA-256 or SHA-384 DS candidates. It also checks the presentation structure of supplied CSYNC and DSYNC records and retains the presence of RRSIG records as unverified context. It does not cryptographically validate those supplied signatures; establish CSYNC or CDS/CDNSKEY consistency across authoritative servers; resolve or contact a DSYNC endpoint; contact a registrar, registry, parent zone, signer, or authoritative provider; discover provider timing policy; verify that supplied records are current; perform RFC 5011; send a notification; or execute a rollover. Its stages are review guidance, not proof that a transition is safe to publish.

## Delegation and external-vantage measurements

Delegation Lab delegates bounded DNS commands to an external measurement network. Probe placement is opportunistic, location requests are selection hints rather than guarantees, some probes or targets may be blocked or unavailable, and the returned resolver, network, ASN, city, country, timing, hop, and raw-output metadata are supplied by that service. At most three probes cannot establish worldwide propagation, consistency, censorship, reachability, or the state seen by a particular user.

A trace follows the measurement service’s DNS trace implementation rather than ZoneSkein’s local DNSSEC validator. An intended-authority test directs each selected probe to one supplied server at a time; a successful recursive or authoritative response does not prove that the parent delegation points there, that every anycast instance behaves identically, or that the server is authorised. External traffic and browser connection metadata cross the privacy and acceptable-use boundary described in `PRIVACY.md` and `TERMS.md`. The six-run hourly browser ledger is an ordinary client-side abuse control and is not tamper-resistant.

## Protocol Lab

Safe numeric queries are still recursive observations and accept only class IN data types outside the unsafe meta-query set. Unknown RDATA is retained in RFC 3597 form without assigning semantics. The bundled IANA mnemonic snapshot is dated source material and can lag a later registry change; numeric input remains available for safely queryable types not yet named by that snapshot.

Resolver information is requested with recursion disabled and is accepted only from an authoritative response. Many recursive services do not publish it or do not expose it through their browser endpoint, so unavailable is normal and is not evidence of non-compliance. ECH configuration decoding checks the bounded list structure and known field shapes; it does not perform a TLS connection, verify server support, validate a public name, or prove that an advertised configuration will succeed.

## SPF

The analyser models lookup-causing terms and follows includes and redirects within bounded depth, work, cardinality, response-byte, and question budgets. It stops at an eleventh DNS-causing term and reports policy term counts separately from the DNS-over-HTTPS questions ZoneSkein made. Void accounting follows individual DNS questions separately for IPv4 and IPv6 sender paths.

The snapshot flattener refuses output when correctness depends on macros, `exists`, `ptr`, cycles, unsupported syntax, non-pass DNS mechanism qualifiers, multiple SPF records, incomplete data, invalid answer shape, lookup or void-limit failures, or exhausted work bounds. Unsafe runs retain no partial network or provenance output. Generated ranges can become stale as providers change infrastructure. Absolute expiry is derived from every required response’s original observation time; if any required expiry is unavailable, aggregate freshness and recheck timing remain unknown. Snapshot output is never published automatically.

Sender-context mode models one supplied SMTP client IP, MAIL FROM identity, HELO/EHLO domain, and optional receiver name against one point-in-time resolver observation. It is not an SMTP transaction and cannot reproduce a receiver's cache, local policy, or delivery decision. SPF macros can place portions of those inputs into DNS question names sent to the selected resolver.

The response-size value is an estimate for a conventional answer and can differ with owner-name compression, DNSSEC records, EDNS, resolver additions, or authoritative-server behaviour.

## Zone snippets, Record Studio, Zone Exchange, Change Lab, and Change Workspace

The zone parser supports a practical subset of comments, quoted TXT strings, parentheses, `$ORIGIN`, `$TTL`, inherited owners, relative names, explicit TTL, IN class, and common types. It is not a complete BIND parser. Provider extensions such as ALIAS, ANAME, proprietary flattening, routing policies, health checks, and provider-side templates require provider validation.

Complete-zone digest mode is opt-in because a digest of a snippet is misleading. It requires one apex SOA, explicit or inherited TTLs, and exact encoding for every included record; preserves raw escaped-name structure and each record's active origin; omits out-of-zone data, duplicate records, apex ZONEMD records, and their covering RRSIG records; and stops when a record cannot be represented without guessing. It supports SIMPLE scheme SHA-384 and SHA-512 calculation for the parser's practical record subset plus RFC 3597 generic RDATA, applying known-type canonicalisation to numeric aliases while retaining genuinely unknown RDATA as opaque bytes, with at most 4,096 parsed records and 2 MiB of canonical wire data. It does not perform AXFR, discover omitted records, or prove that the supplied text is the currently published complete zone. A matching digest without a separately validated covering DNSSEC chain establishes internal consistency only, not source authenticity or resistance to deliberate replacement. Live DNSSEC inspection can authenticate a selected published ZONEMD RRset, but that authentication alone cannot show that locally supplied zone contents match it.

Record Studio serialises 18 supported record types and applies the practical zone linter to a bounded local working set. It does not know provider-specific syntax, account permissions, existing authoritative records, signing policy, or the intended zone cut, and it never publishes records.

Zone Exchange expands only files explicitly selected together in the browser. Its `$INCLUDE` and `$GENERATE` implementation is bounded and intentionally excludes named-file loading outside that bundle, shell expansion, provider extensions, and arbitrary directive execution. Expanded output preserves source-line provenance but is not proof that the source bundle was complete, authentic, current, or accepted by a particular name server.

Service-template preview validates and instantiates the supported common record actions. Provider-specific redirect, apex-alias, grouping, conflict, synchronisation, credential, and publication behaviour remains explicit or unsupported. Portable configuration output covers only records that can be represented conservatively in both draft formats; diagnostics and omissions must be reviewed, and generated text is not guaranteed to match a later tool version or provider policy. ZoneSkein never runs a target configuration tool or publishes the draft.

Change Lab normalisation treats ordinary RRset ordering as non-semantic and recognises selected name and numeric fields. Its risk and timing guidance is derived only from supplied or selected records. Unselected RR types, provider behaviour, application dependencies, and recursive-cache state remain outside its evidence, so it cannot assign a universal propagation-complete time.

Relative targets use each record's active origin, independently of the zone apex used for in-zone checks. Quoted data retains its whitespace and token boundaries. Equality evidence distinguishes canonical-wire equality, known SPF application equivalence, opaque-data equality and unsupported semantics without changing the existing change categories. TXT concatenation equivalence does not imply identical wire strings or establish an unknown application's interpretation.

Change Workspace carries bounded current and intended BIND-style text, explicit complete, partial, or unavailable state, structured Change Lab analysis, and optional historical resolver evidence. It does not discover missing records, poll propagation, publish DNS, persist automatically, or authenticate an author. Import validation checks structure and internal consistency; it does not reproduce or endorse stored analysis, which remains supplied historical data until local reanalysis. A SHA-256 mismatch shows that the content no longer matches the included digest; a match shows internal consistency only because anyone modifying the file can recompute its digest. Imported resolver endpoints are inert provenance and are never queried. Local reanalysis is blocked when either zone state is unavailable and remains partial when an input is partial, so unknown data is never interpreted as an empty zone.

Workspace JSON, snapshots, copied evidence, share fragments, and source-archive checksums are not encryption or signatures. Visitors are responsible for having authority to process the data they enter and for protecting every export and recipient they choose.

Validated imports wait for explicit replacement; cancellation and navigation invalidate pending work. Unapplied edits must be applied before analysis or export. The optional `zoneskein-workspace-validation-report-v1` sidecar binds the workspace digest to a source fingerprint, available Git revision and validation status. It is separate from the unchanged `zoneskein-project-v1` envelope, and identifies supplied/prior analysis versus recomputation in the current session. Neither report authenticates an author.

## Mail reports, transport policy, DMARC, DKIM, BIMI, ARC, and CAA

Mail Lab parses bounded DMARC aggregate XML and TLS report JSON from direct, gzip, or ZIP input. It does not authenticate the report sender, verify XML signatures, establish delivery completeness, deduplicate reports across files, infer events outside the reported interval, or reproduce a receiver’s policy. Aggregate counts and failure samples are claims in the supplied files. Archive and parser limits can reject otherwise valid large reports.

MTA-STS and TLS reporting helpers inspect or author the supported policy and record shapes locally. They do not fetch `mta-sts` policy URLs, resolve MX records automatically, connect with SMTP STARTTLS, validate a live certificate chain, submit reports, or determine whether a receiver will enforce a policy. MX coverage compares only the supplied names against supplied policy patterns.

Certificate inspection parses one bounded X.509 object and can compare selected DER or public-key bytes with a TLSA association using supported matching modes. It does not build or validate a certificate chain, check revocation, perform hostname validation, establish DNSSEC authentication of the TLSA record, evaluate usage semantics, contact a TLS service, or prove DANE deployment. A byte match is reported separately from those missing trust decisions.

BIMI inspection validates a record shape and parses supplied SVG against a conservative static profile without fetching it or rendering supplied markup. It does not verify a Verified Mark Certificate, trademark entitlement, DMARC enforcement, logo hosting, receiver support, or display. ARC inspection is structural only: it groups bounded header sets and checks instance continuity and required fields, but does not canonicalise content, fetch keys, verify signatures or seals, or establish chain validity.

DMARC policy mode follows the bounded RFC 9989 DNS Tree Walk, validates published policy syntax, and checks RFC 9990 and RFC 9991 external-reporting authorisation records. Alignment mode accepts an RFC5322.From domain, already-passing DKIM `d=` domains, and an SPF result with its authenticated MAIL FROM domain. Those results can be entered manually, moved in memory from the SPF or DKIM route, or imported through the strict minimal hand-off schema. Transfer preserves provenance and reconstruction caveats but does not reverify the source run, recreate its DNS observation, prove freshness, or change the selected resolver; editing a transferred field detaches its provenance. It does not parse or authenticate a message; every alignment conclusion is conditional on the supplied prior authentication evidence, the selected resolver observation, and completed organisational-boundary walks. It does not apply ARC or receiver-local policy, test report delivery, or predict enforcement.

DKIM key mode validates one supplied selector and imports supported public keys; it does not discover selectors. Message mode locally parses a bounded pasted message or byte-preserving `.eml` file and verifies at most 20 RSA-SHA256 or Ed25519-SHA256 signatures. Other algorithms, ARC, DMARC alignment, sender reputation, and delivery are outside its scope. Pasted text with reconstructed CRLF is labelled accordingly, and an `l=` signature authenticates only its signed body prefix.

CAA inspection follows a bounded parent walk and explains the first observed policy, including standardised account, validation-method, and S/MIME controls. It does not authenticate a certificate request, interpret every CA-specific parameter, or guarantee that issuance succeeds or fails.

## Abuse controls

Browser rate limits and input bounds protect the normal direct paths. Origin-wide browser locks make a shared DNS reservation atomic where supported; browsers without them retain best-effort cross-tab coordination. These controls are not tamper-resistant and cannot constrain a modified client. Quad9 compatibility mode separately enforces its own fixed target, method, media type, query shape, request and response size, DNS work, timeout, and 120-request-per-minute rate limit per source IP address and site domain. Visitors behind one apparent egress address can share that allowance, while distributed source addresses have separate allowances; it is not an absolute site-wide upstream cap. Delegation Lab’s six-run hourly timestamp ledger is also client-side and the fixed measurement service enforces separate policies and limits. Those controls reduce ordinary abuse but do not make recursive or external-vantage results authoritative or prove global propagation.
